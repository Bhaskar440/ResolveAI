# 03 — API Specification

Base: `https://api.<host>/api/v1` · JSON only · OpenAPI 3.1 auto-generated by FastAPI at `/api/v1/openapi.json`
(TS types generated into `apps/web/src/types/api.d.ts`). Auth: `Authorization: Bearer <access_token>`.

## 0. Conventions

- **Errors** (RFC 9457-ish, single envelope):
  `{ "error": { "code": "POLICY_DENIED", "message": "Refund exceeds merchant cap", "details": {...}, "request_id": "...", "retryable": false } }`
  Codes: `UNAUTHENTICATED 401`, `FORBIDDEN 403`, `NOT_FOUND 404`, `VALIDATION_ERROR 422`, `STATE_CONFLICT 409`, `POLICY_DENIED 403`, `APPROVAL_REQUIRED 409`, `IDEMPOTENCY_CONFLICT 409`, `PAYPAL_UNAVAILABLE 502`, `RATE_LIMITED 429`, `BUDGET_EXCEEDED 422`.
- **Pagination:** cursor-based: `?limit=50&cursor=<opaque>` → `{ "items": [...], "next_cursor": "...", "total_estimate": 128 }`. Max limit 200.
- **Idempotency:** all `POST` accept `Idempotency-Key`; replay within 24h returns the original response with `Idempotency-Replayed: true`.
- **Concurrency:** `GET` returns `ETag`; mutating control endpoints require `If-Match` → `412` on mismatch.
- **RBAC:** `viewer` (read), `analyst` (read + approve + manual action), `owner` (all + settings + credentials).
- **Field naming:** `snake_case` in JSON (matches Python); TS client maps to camelCase at the boundary.

## 1. Auth

| Method | Path | Notes |
|---|---|---|
| POST | `/auth/login` | `{email, password}` → `{access_token, token_type, expires_in, user}`. Access 30 min, refresh cookie 7 d. Rate limit 5/min/IP. |
| POST | `/auth/refresh` | httpOnly refresh cookie → new access token. |
| POST | `/auth/logout` | revokes refresh. |
| GET | `/auth/me` | `{user, merchant, permissions[], mode:{paypal:"sandbox"\|"replay", autonomy:true}}` — the frontend reads `mode` for the header badge. |

Hackathon simplification: seeded users; no signup. `POST /auth/login` is the only credential flow.

## 2. Disputes

### `GET /disputes` — grid data source
Query: `status[]`, `reason_code[]`, `decision_code[]`, `q` (search case number/buyer label), `min_amount`, `max_amount`, `due_before`, `sort` (`-created_at` default; allowed: `created_at, amount, response_due_by, priority`), `cursor`, `limit`.

```json
{
  "items": [{
    "id": "d_01J...", "paypal_case_number": "PP-D-12345",
    "status": "AWAITING_APPROVAL", "paypal_status": "WAITING_FOR_SELLER_RESPONSE",
    "reason_code": "MERCHANDISE_OR_SERVICE_NOT_RECEIVED",
    "amount": 80.00, "currency": "USD",
    "buyer_label": "Buyer #3f2a",
    "response_due_by": "2026-11-12T18:00:00Z",
    "sla": { "state": "due_soon", "hours_left": 21.4 },
    "confidence": 0.62,
    "decision_code": "OFFER_PARTIAL",
    "requires_approval": true,
    "agent_summary": "Tracking shows delivered; buyer contests address. Proposing 50% offer.",
    "updated_at": "2026-11-11T09:12:03Z"
  }],
  "next_cursor": "eyJvIjoyMH0", "total_estimate": 34
}
```
`agent_summary` is denormalized on the dispute row (written at decision time) so the grid needs one query.

```json
{
  "dispute": { "...full row..." },
  "order": { "paypal_order_id": "...", "amount": 80.00, "created_at_paypal": "..." },
  "capture": { "paypal_capture_id": "...", "seller_protection_status": "ELIGIBLE", "status": "COMPLETED" },
  "buyer": { "label": "Buyer #3f2a", "lifetime_dispute_count": 1 },
  "latest_run": { "id": "r_01J...", "status": "AWAITING_APPROVAL", "started_at": "...", "cost_usd": 0.041 },
  "decision": { "id": "dec_...", "decision_code": "OFFER_PARTIAL", "amount": 40.00, "confidence": 0.62,
                "rationale": "...", "cited_evidence": ["ev_1","ev_3"], "requires_approval": true,
                "policy_eval": { "result": "require_approval", "ruleset_version": "2026.11.1",
                                 "matched_rules": [{"id":"AMOUNT_ABOVE_AUTO_CAP","outcome":"require_approval"}] } },
  "pending_approval": { "id": "ap_...", "expires_at": "...", "can_edit_amount": true },
  "evidence": [ { "id": "ev_1", "kind": "tracking", "filename": "ups_tracking.pdf", "sha256": "..." } ],
  "timeline": [ { "at": "...", "actor": "agent:resolution", "type": "decision_proposed", "summary": "..." } ],
  "available_actions": ["approve", "reject", "edit_and_approve", "escalate", "request_info", "upload_evidence", "rerun"]
```

`available_actions` is computed server-side from state + role + policy — the UI renders buttons from it instead of guessing.

### Other dispute endpoints
| Method | Path | Purpose |
|---|---|---|
| GET | `/disputes/{id}/timeline` | Paginated `dispute_status_history` + `dispute_messages` + key run events, merged. |
| GET | `/disputes/{id}/messages` | Thread; `POST` adds a merchant message (queued to PayPal `send-message` after approval). |
| POST | `/disputes/{id}/actions/{action}` | `action ∈ {approve, reject, edit_and_approve, escalate, request_info, rerun, mark_resolved, snooze}`. Body: `{note?, amount?, if_match_version}`. Returns `202 {run_id}` or `200 {dispute}`. |
| POST | `/disputes/{id}/sync` | Force a PayPal refresh (rate-limited 1/10s/dispute). |
| GET | `/disputes/{id}/export` | CSV/PDF dossier (evidence + rationale) for a human appeal. |

`approve` semantics: resolves the pending LangGraph `interrupt`, then execution proceeds. Response is
`202` with `run_id`; the UI follows the SSE stream. Editing the amount re-runs the policy gate
(re-validation is mandatory — the UI cannot bypass the cap).

## 4. Runs & agent trace

| Method | Path | Purpose |
|---|---|---|
| POST | `/disputes/{id}/runs` | Start orchestration. Body `{force?: bool}`. → `202 {run_id, thread_id}`; `409 RUN_ALREADY_ACTIVE` if one is running. |
| GET | `/runs/{run_id}` | Status, budgets consumed, model, cost, error. |
| GET | `/runs/{run_id}/steps?after_seq=` | Ordered trace (polling fallback for SSE). |
| GET | `/runs/{run_id}/messages` | Typed agent handoff transcript — rendered as the "negotiation" view. |
| POST | `/runs/{run_id}/resume` | `{decision:"approve"\|"reject", edited_amount?, note?}` → resumes the interrupt. `409` if not awaiting. |
| POST | `/runs/{run_id}/cancel` | Cooperative cancel; sets a checkpoint flag. |
| GET | `/disputes/{id}/stream` | **SSE** (see §7). |

## 5. Payments (read + controlled write)

| Method | Path | Purpose |
|---|---|---|
| GET | `/payments/orders/{paypal_order_id}` | Live PayPal lookup (Payment Agent's read tool surfaced for humans). |
| GET | `/payments/captures/{paypal_capture_id}` | Includes seller protection + dispute IDs. |
| POST | `/payments/refunds` | **Owner/analyst only, always policy-gated.** `{capture_id, amount, reason, dispute_id?, idempotency_key}` → `202 {refund_id, status}`. Requires an approved decision unless `override_reason` is set (which is audited and capped). |
| GET | `/payments/refunds/{id}` | Status + PayPal payload. |

## 6. Webhooks & admin

| Method | Path | Purpose |
|---|---|---|
| POST | `/webhooks/paypal` | **Unauthenticated but signature-verified.** Reads raw body, verifies `PAYPAL-TRANSMISSION-*` headers, dedupes on `event.id`, writes outbox, returns `200` in <300 ms. Any processing error → still `200` (we retry internally); only signature failure → `400`. |
| POST | `/webhooks/paypal/simulate` | Dev/`replay` mode only: inject a fixture event (`?fixture=inr_created`). 404 in sandbox/live. |
| GET | `/health/live`, `/health/ready` | Liveness / readiness (DB + config check). |
| GET | `/admin/status` | Mode, kill switch, queue depth, last webhook age, PayPal circuit state. |
| POST | `/admin/autonomy` | `{enabled: bool, reason}` — kill switch, audited. |
| POST | `/admin/replay/{run_id}` | Re-run a stored run against fixtures (deterministic demo). |
| POST | `/admin/reset-demo` | Wipe + reseed demo data. Guarded by `ALLOW_ADMIN_RESET=true`. |
| GET | `/admin/audit/verify` | Verifies the audit hash chain. |

## 8. SSE contract — `GET /disputes/{id}/stream` and `/stream` (global)

```
event: run.step
data: {"run_id":"r_1","seq":14,"node":"resolution_agent","agent":"resolution","type":"llm_call","summary":"Weighing POD vs. buyer claim","at":"..."}

event: run.interrupt
data: {"run_id":"r_1","approval_id":"ap_1","decision_code":"OFFER_PARTIAL","amount":40.0,"expires_at":"..."}

event: dispute.updated
data: {"id":"d_1","status":"RESOLVED","decision_code":"REFUND_FULL","at":"..."}

event: heartbeat        (every 15s, keeps proxies alive)
```
Implementation: in-process `asyncio.Queue` registry per merchant (single API instance for MVP; Redis pub/sub
only if we scale out). Client uses `EventSource` with auto-reconnect + `Last-Event-ID`; on reconnect the UI
refetches the detail aggregate and resumes from `seq`.

## 9. Buyer channel (simulated, clearly labeled)

| Method | Path | Purpose |
|---|---|---|
| POST | `/buyer/complaints` | `{order_id, email, message, requested_remedy?}` → creates a *pre-dispute inquiry* (channel=`buyer_api`), runs the Buyer agent, may auto-resolve before a PayPal dispute exists. |
| POST | `/buyer/disputes/{id}/messages` | Buyer reply into the negotiation thread. |
| GET | `/buyer/disputes/{id}` | Buyer-visible view (no internal rationale, no merchant policy) — proves the RBAC/citation separation. |

This is the hackathon stand-in for email/chat ingestion. It demonstrates "resolve before it escalates,"
which is the strongest business story, and it costs one endpoint.

## 10. Example: end-to-end sequence (API level)

```
POST /webhooks/paypal            → 200
SSE  dispute.created             → grid row
POST /disputes/{id}/runs         → 202 {run_id}
SSE  run.step × N                → trace panel fills
SSE  run.interrupt               → approval dialog appears
POST /runs/{run_id}/resume       → 202
SSE  run.step (execute)          → spinner
SSE  dispute.updated RESOLVED    → row turns green, refund id shown
GET  /disputes/{id}              → full audit-ready dossier
```
